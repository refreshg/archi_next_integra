# Archi-ს მხარეს აწყობის ინსტრუქცია

> ⚠️ **მოძველებულია 2026-09-20-დან.** ეს დოკუმენტი webhook-აქტივობით აწყობას აღწერს.
> რეალურად გამოიყენება **PHP Code** აქტივობა — მიმდინარე ინსტრუქცია და კოდი:
> [docs/bp/block.php](bp/block.php), აწყობის ნაბიჯები — [README.md](../README.md) ეტაპი 3.

ეს დოკუმენტი განკუთვნილია იმისთვის, ვინც Archi-ს ბიტრიქსში **ხელით** აწყობს ბიზნეს პროცესს.
კოდი ამ ნაბიჯებში არ მონაწილეობს — რეპოზიტორია მხოლოდ ზუსტ პარამეტრებს გაძლევს.

ორივე პორტალი **box** (საკუთარ სერვერზე) ვერსიაა, ამიტომ მენიუს სახელები შეიძლება
ოდნავ განსხვავდებოდეს ვერსიის მიხედვით. ქვემოთ ქართული და რუსული ვარიანტებია მოცემული.

## ნაბიჯი 1 — შემომავალი webhook Next-ზე

Next-ის პორტალზე (`https://bitrix.nextgroup.ge`), ადმინის უფლებით:

1. `აპლიკაციები` (Приложения) → `ვებჰუკები` (Вебхуки) → `დაამატე ვებჰუკი` → **`შემომავალი ვებჰუკი`**
2. მონიშნე უფლებები: **`CRM (crm)`**, **`სავაჭრო კატალოგი (catalog)`**, **`მომხმარებლები (user)`**
3. შეინახე და დააკოპირე მიღებული URL:
   ```
   https://bitrix.nextgroup.ge/rest/<USER_ID>/<TOKEN>/
   ```

> 💡 შექმენი ცალკე ტექნიკური მომხმარებლით (არა პირადი ადმინის ანგარიშით) — თანამშრომლის
> წასვლისას ინტეგრაცია არ გაჩერდება. ამ მომხმარებელს კატალოგზე ჩაწერის უფლება უნდა ჰქონდეს.

**რისკი:** box ვერსიაზე შეიძლება `rest` მოდული არ იყოს დაინსტალირებული. თუ მენიუში „ვებჰუკები"
საერთოდ არ ჩანს — ჯერ `rest` მოდული უნდა დაინსტალირდეს Marketplace-იდან.

## ნაბიჯი 2 — მონაცემების შემოწმება Next-ზე

სანამ ბიზნეს პროცესზე გადახვალ:

- სასინქრონიზებელ პროდუქტებს **უნდა ჰქონდეთ შევსებული `UF_ARCHI_ID`**. თუ ცარიელია,
  ინტეგრაცია ამ პროდუქტს ვერ იპოვის.
- დაფიქსირდეს სტატუსის ველის **ზუსტი კოდი** და სამივე მნიშვნელობის **რიცხვითი ID**.

ეს ორივე ავტომატურად ამოდის:

```bash
npm run discover      # შედეგი: docs/next-fields.md
```

თუ ხელით ამჯობინებ: პროდუქტის ველის პარამეტრებში ჩანს კოდი (`UF_...` ან `PROPERTY_<id>`),
სიის მნიშვნელობების ID-ები კი — ველის რედაქტირების ფორმაში.

> ❗ სტატუსში იწერება **მნიშვნელობის ID** (მაგ. `47`), და არა ტექსტი „რეზერვი".

## ნაბიჯი 3 — ბიზნეს პროცესის შექმნა Archi-ზე

1. `CRM` → `გარიგებები` → `პარამეტრები` / `ავტომატიზაცია` → **`ბიზნეს პროცესები`**
   (Настройки → Бизнес-процессы)
2. `შექმენი ახალი` → ტიპი: **თანმიმდევრული** (Последовательный)
3. დაარქვი გასაგები სახელი, მაგ. `Next — პროდუქტის სტატუსის განახლება`

### 3.1 პირობის ბლოკი

დაამატე **`პირობა`** (Условие) ბლოკი, სამი ტოტით — თითო სტატუსზე:

| ტოტი | პირობა | რა სტატუსი იგზავნება |
|---|---|---|
| 1 | გარიგების სტადია ∈ რეზერვის სტადიები | `რეზერვი` |
| 2 | გარიგების სტადია ∈ გაყიდვის სტადიები | `გაყიდული` |
| 3 | გარიგების სტადია ∈ გაუქმების სტადიები | `თავისუფალი` |

რომელი სტადია რომელ ტოტში მოხვდება — **შენ წყვეტ**. კოდში ეს არსად არ წერია და
ცვლილებისთვის არაფრის გადაწერა არ დაგჭირდება.

### 3.2 webhook-ის გამოძახება

თითო ტოტში დაამატე აქტივობა **`Webhook-ის გამოძახება`** (Вызов вебхука) —
ეძებე განყოფილებაში `სხვა` (Прочее).

პარამეტრები მიიღე ბრძანებით:

```bash
npm run bp-payload
```

ის დაბეჭდავს თითო სტატუსზე ზუსტად ამ სტრუქტურას:

| ველი | მნიშვნელობა |
|---|---|
| მეთოდი | `POST` |
| URL | `https://bitrix.nextgroup.ge/rest/<USER_ID>/<TOKEN>/batch.json` |
| `halt` | `1` |
| `cmd[find]` | `crm.product.list?...filter[UF_ARCHI_ID]={=Document:UF_CRM_XXXX}...` |
| `cmd[upd]` | `crm.product.update?id=$result[find][0][ID]&fields[<სტატუსის ველი>]=<ID>` |

რას აკეთებს:

- `cmd[find]` — პოულობს პროდუქტს Next-ში Archi-ს ID-ით
- `cmd[upd]` — `$result[find]`-იდან იღებს ნაპოვნის შიდა ID-ს და ცვლის სტატუსს
- `halt=1` — თუ ძებნა ჩავარდა, განახლება **აღარ შესრულდება** (ვერ შეიცვლება შემთხვევითი პროდუქტი)

> ფრჩხილები `%5B` `%5D` სახით ჩანს — ეს სწორია, ბიტრიქსი თვითონ გაშიფრავს.
> `{=Document:UF_CRM_XXXX}` — ჩაანაცვლე გარიგების იმ ველით, სადაც პროდუქტის ID წერია.

### 3.3 შეცდომების დამუშავება

აქტივობის პასუხი შეინახე ცვლადში (მაგ. `webhookResponse`), შემდეგ დაამატე პირობა:

| შემთხვევა | რა ნიშნავს | რა ქნას პროცესმა |
|---|---|---|
| პასუხში `result_error` არაცარიელია | ძებნა ან განახლება ჩავარდა | კომენტარი გარიგებაზე + შეტყობინება პასუხისმგებელს |
| პასუხი ცარიელია / HTTP შეცდომა | Next მიუწვდომელია | იგივე |
| წარმატება | სტატუსი შეიცვალა | (სურვილისამებრ) კომენტარი ტაიმლაინში |

ეს ნაბიჯი **სავალდებულოა**: ამ არქიტექტურაში გარიგების ტაიმლაინი ერთადერთი ლოგია.
თუ ის არ არის, ჩავარდნილი სინქრონიზაცია უხმაუროდ დაიკარგება.

## ნაბიჯი 4 — გაშვება

`CRM` → `გარიგებები` → `ავტომატიზაცია` → საჭირო სტადიებზე დაამატე წესი,
რომელიც ამ ბიზნეს პროცესს უშვებს.

ალტერნატივა: ბიზნეს პროცესის პარამეტრებში მონიშნე „ავტომატური გაშვება ჩანაწერის ცვლილებისას".
ამ შემთხვევაში პირობის ბლოკი თვითონ გაფილტრავს, სტადია შეიცვალა თუ არა.

## ნაბიჯი 5 — ტესტირება

რეალურ პორტალზე ვმუშაობთ, ამიტომ ჯერ **სატესტო პროდუქტზე**:

| # | ქმედება | მოსალოდნელი შედეგი |
|---|---|---|
| 1 | სატესტო გარიგება → რეზერვის სტადია | Next-ში სტატუსი = რეზერვი, 1 წუთში |
| 2 | იგივე გარიგება → გაყიდვის სტადია | სტატუსი = გაყიდული |
| 3 | გარიგების გაუქმება | სტატუსი = თავისუფალი |
| 4 | გარიგება არასწორი პროდუქტის ID-ით | არცერთი პროდუქტი არ შეცვლილა, ტაიმლაინში შეცდომა |
| 5 | იგივე სტატუსი ორჯერ | ორივეჯერ წარმატება, შედეგი არ იცვლება |

ბიზნეს პროცესზე გადასვლამდე იგივე ტესტები გაუშვი კონსოლიდან:

```bash
npm run set-status -- --product <ARCHI_ID> --status reserved --dry-run
npm run set-status -- --product <ARCHI_ID> --status reserved
```

## R-1 — რისკი: აქტივობა შეიძლება არ არსებობდეს

box ვერსიები ღრუბელს ჩამორჩება. თუ ბიზნეს პროცესის დიზაინერში `Webhook-ის გამოძახება`
ვერ იპოვე, სცადე შემდეგი, ამ თანმიმდევრობით:

1. **ავტომატიზაციის რობოტი „ვებჰუკი"** — `CRM` → `ავტომატიზაცია` → რობოტის დამატება.
   თუ არსებობს, იგივე პარამეტრები იქ ჩაისმება, ბიზნეს პროცესის გარეშე.
2. **PHP აქტივობა Archi-ს box-ზე** — მოითხოვს სერვერზე წვდომას და დეველოპერულ სამუშაოს.
3. **შუალედური სერვისი (middleware)** — ბოლო ვარიანტი; ცვლის საბაზისო არქიტექტურას
   (იხ. `docs/DECISIONS.md`, D-1 და D-8).

**გადაწყდა 2026-09-20:** არცერთი ამ ვარიანტიდან არ დასჭირდა — box-ს აქვს **PHP Code** აქტივობა
და სწორედ ის გამოიყენება. იხ. `docs/DECISIONS.md`, D-11.
