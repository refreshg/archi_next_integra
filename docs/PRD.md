# პროდუქტის სტატუსის სინქრონიზაცია Archi ↔ Next

## Problem

გაყიდვების პროცესი Archi-ს ბიტრიქსში მიმდინარეობს, პროდუქტების (ბინების) კატალოგი კი
Next-ის ბიტრიქსშია. როცა Archi-ში გარიგება რეზერვის ან გაყიდვის სტადიაზე გადადის,
Next-ში პროდუქტის სტატუსს ხელით ცვლიან.

ხელით ცვლილება აგვიანებს და ზოგჯერ საერთოდ არ ხდება — შედეგად Next-ის კატალოგში
გაყიდული ან დარეზერვებული პროდუქტი თავისუფლად ჩანს. ეს იწვევს ორმაგ რეზერვაციას და
არასწორ ინფორმაციას.

## Users / roles

| როლი | რას აკეთებს | სიხშირე |
|---|---|---|
| გაყიდვების მენეჯერი (Archi) | გარიგებას სტადიებზე გადაჰყავს — ეს არის ერთადერთი მოქმედება, რაც სინქრონიზაციას იწვევს | დღეში ~10 გარიგება |
| ადმინისტრატორი (Next) | პროდუქტების კატალოგს უვლის, სტატუსის სისწორეს ამოწმებს | ყოველდღიურად |
| ინტეგრაციის მფლობელი | ბიზნეს პროცესს და webhook-ებს ქმნის და უვლის | დაყენებისას, შემდეგ იშვიათად |

## User stories

- **US-1** — როგორც გაყიდვების მენეჯერს, მინდა გარიგების სტადიის შეცვლისას Next-ში
  პროდუქტის სტატუსი ავტომატურად შეიცვალოს, რომ ხელით არაფერი მჭირდებოდეს.
- **US-2** — როგორც Next-ის ადმინისტრატორს, მინდა კატალოგში სტატუსი რეალობას ემთხვეოდეს,
  რომ დარეზერვებული პროდუქტი თავისუფლად არ ჩანდეს.
- **US-3** — როგორც ინტეგრაციის მფლობელს, მინდა ვიცოდე როდის ჩავარდა სინქრონიზაცია,
  რომ ხელით გავასწორო და მიზეზი დავადგინო.
- **US-4** — როგორც გაყიდვების მენეჯერს, მინდა რეზერვის გაუქმებისას პროდუქტი ისევ
  თავისუფალი გახდეს, რომ ხელახლა გაიყიდოს.

## In scope

- Archi-ს გარიგების სტადიის ცვლილება → Next-ში პროდუქტის სტატუსის ცვლილება.
- ოთხი სტატუსი, ზუსტად ისე, როგორც Next-ში იწერება:
  **თავისუფალი / უფასო ჯავშანი / ფასიანი ჯავშანი / გაყიდული**.
  სამი უკანასკნელი **დაცულია** — მათ მხოლოდ დამდები მხარე ცვლის (D-18).
- პროდუქტის დამთხვევა Next-ის `UF_ARCHI_ID` (`PROPERTY_546`) ველით.
- უკუმიმართულება Next → Archi (მფლობელი ქმნის შესაბამის webhook-ს Archi-ს მხარეს).
- **Next-ის მხარეს ცალკე ბიზნეს პროცესი** (BP 39 „Archi_integra"), რომელიც იმავე ველში ლოგავს
  და მომხმარებლის სახელსაც წერს (D-15).
- შეცდომის დაფიქსირება გარიგების ტაიმლაინში და შეტყობინება პასუხისმგებელთან.

## Out of scope

- სხვა ველების სინქრონიზაცია — ფასი, დასახელება, ფოტო, აღწერა. **მხოლოდ სტატუსი.**
- პროდუქტის შექმნა ან წაშლა რომელიმე პორტალში.
- ისტორიული მონაცემების უკუსინქრონიზაცია (არსებული შეუსაბამობების გასწორება).
- შუალედური სერვისი (middleware), რიგები, retry-ს ინფრასტრუქტურა.
- Archi-ს პროდუქტის ან გარიგების შეცვლა — ინტეგრაცია Archi-ს მხარეს მხოლოდ კითხულობს.

## Acceptance criteria

- **AC-1** (US-1) — მოცემულია გარიგება Archi-ში, რომლის პროდუქტის ID არსებობს Next-ში;
  როცა გარიგება რეზერვის სტადიაზე გადადის, Next-ში ამ პროდუქტის სტატუსი ხდება **„ფასიანი ჯავშანი"**.
- **AC-2** (US-1) — იგივე პირობებში, გაყიდვის სტადიაზე გადასვლისას სტატუსი ხდება „გაყიდული".
- **AC-3** (US-4) — გარიგების გაუქმებისას სტატუსი ხდება „თავისუფალი".
- **AC-4** (US-3) — თუ მითითებული ID-ით Next-ში პროდუქტი ვერ მოიძებნა, არცერთი პროდუქტის
  სტატუსი არ იცვლება, გარიგების ტაიმლაინში იწერება შეცდომა და პასუხისმგებელი იღებს შეტყობინებას.
- **AC-5** (US-3) — თუ Next მიუწვდომელია ან webhook აბრუნებს შეცდომას, გარიგება არ იჭედება
  და ტაიმლაინში ფიქსირდება წარუმატებლობა.
- **AC-6a** (US-2) — თუ ბინას უკვე აქვს მოთხოვნილი სტატუსი და ის **დაცული არ არის**, ჩაწერა არ ხდება,
  შეცდომა არ ბრუნდება, ჟურნალში ფიქსირდება `UNCHANGED`.
- **AC-6b** (US-2) — თუ ბინას უკვე აქვს მოთხოვნილი **დაცული** სტატუსი, ჩაწერა არ ხდება და
  ფიქსირდება `REJECTED_SAME` — ეს კონფლიქტია და ყურადღებას მოითხოვს.
- **AC-8** (US-2) — თუ დაცული სტატუსი მეორე მხარემ დააყენა, ცვლილება უარყოფილია (`REJECTED_FOREIGN`)
  და სტატუსი უცვლელი რჩება. ეს ორივე მიმართულებით მოქმედებს (D-18).
- **AC-7** (US-1) — სტატუსის ცვლილება Next-ში ჩანს გარიგების სტადიის შეცვლიდან 1 წუთში.

## Non-functional

- **წარმადობა:** დღეში ≤10 გაშვება. თითო ცვლილება = 2 HTTP მოთხოვნა. ლიმიტების რისკი არ დგას.
  გაზომილი ხანგრძლივობა Archi-ს box-იდან: 6.5–7.5 წამი.
- **უფლებები:** webhook იქმნება ცალკე ტექნიკური მომხმარებლით, არა პირადი ადმინის ანგარიშით.
- **აუდიტი:** ყოველი გაშვება სამ ადგილას ფიქსირდება — BP-ს ჟურნალი, BP ცვლადები
  (`Logstat` + `Send_log`) და Next-ის პროდუქტის `Interga_History` ველი.
- **ენა:** ინტერფეისი და შეტყობინებები ქართულად.
- **მობილური:** ცალკე მოთხოვნა არ არის — ბიტრიქსის სტანდარტული აპლიკაცია საკმარისია.
- **ვადა:** 2026-09-25 (1 კვირა).
